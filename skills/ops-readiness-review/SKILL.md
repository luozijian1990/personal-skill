# 运维就绪审查

判断一个运维软件是否具备与其真实风险相匹配的生产运行和操作安全基础。默认只审查，不自动大规模修改产品代码，也不替代 `code-review`、安全测试、E2E 或人工验收。

## 所处流程

```text
实现
→ 代码审查
→ 运维就绪审查
→ E2E 测试计划
→ Playwright E2E
→ 人工验收
```

`code-review` 关注代码质量与 Spec 符合度；本 Skill 关注运行正确性：软件在真实环境中操作基础设施、处理失败和长期运行时是否安全、可恢复、可观察。

## 输入优先级

按实际存在的材料读取：

1. `AGENTS.md`、`CONTEXT.md` 和相关 ADR；
2. Spec、Architecture、stack-selection 和相关 Tickets；
3. 关键产品代码、API、权限与审计实现；
4. Deployment Manifest、配置、迁移与运维文档；
5. 新鲜的 test/build/lint、E2E 或运行证据。

材料不全不等于自动失败。记录已检查范围、缺少的证据及其对结论的影响；关键风险无法验证时，不得给 `PASS`。

## 核心原则

- **风险校准**：只读 Dashboard、普通 CRUD、Kubernetes 管理和 SSH 批量执行需要不同深度。允许 `NOT_APPLICABLE`。
- **证据优先**：区分源码推断、配置证据、自动测试和真实运行验证，不能把计划文档当成实现证据。
- **不按清单堆基础设施**：不因有异步任务就自动要求 MQ，不因有指标就自动要求 OpenTelemetry，不因部署到 Kubernetes 就自动要求 Operator、Service Mesh 或 HA。
- **高风险能力提高门槛**：删除、重启、扩缩容、驱逐、回滚、远程执行和批量操作要同时看授权、确认、审计、幂等、爆炸半径和恢复。
- **复用已有基础设施**：已有 SSO、Secret 管理、数据库、日志和监控优先于新增组件。
- **默认审查，不替用户接受风险**：风险接受必须有责任人和依据，不能由 Agent 自行降级。

## 工作流

### 1. 建立系统风险画像

先用一段话说明：

- 用户与信任边界；
- 管理的目标系统和资源范围；
- 只读还是可变更，是否包含批量/破坏性操作；
- 同步请求、定时任务或长任务；
- 部署拓扑、持久化和外部依赖；
- 生产环境约束与已有基础设施。

信息不足时把会改变严重度的问题列为 `Unknown`，不要脑补。

### 2. 建立证据索引

把每项关键结论关联到文件、配置、测试或运行证据。证据等级：

- `DOCUMENTED`：仅设计或文档声明；
- `STATIC`：代码或配置可见；
- `TESTED`：自动测试有新鲜结果；
- `RUNTIME_VERIFIED`：在目标或等价环境实际验证。

文档承诺不能单独证明生产就绪。

严格区分两类措辞：

- **已证实缺失**：代码、配置或运行结果明确显示控制不存在或失效；可以形成缺陷 Finding。
- **证据不足**：当前材料无法证明控制存在或有效；标记 `NOT_VERIFIED`，不要写成“系统没有该控制”。

### 3. 执行按风险裁剪的检查

读取 [`references/readiness-checklist.md`](references/readiness-checklist.md)，覆盖适用领域：

1. Destructive Operations
2. Authentication / Authorization
3. Audit
4. Secret / Credential
5. Remote Execution
6. Kubernetes Operations
7. Async Jobs
8. API Reliability
9. Observability
10. Data Lifecycle
11. Deployment
12. Failure / Recovery

每个领域标记 `ASSESSED`、`NOT_APPLICABLE` 或 `NOT_VERIFIED`，并简述理由。不要省略不适用理由，也不要把不适用误写为已通过。

### 4. 评定严重度

- **BLOCKER**：可能造成越权、跨租户访问、Secret 泄露、不可控破坏、无限制远程执行/并发，或关键失败会造成不可接受且无恢复路径的风险。发布前必须解决。
- **MAJOR**：重要可靠性、安全或可运维性缺口；当前可能有人工绕行，但不适合无条件进入生产。
- **MINOR**：影响诊断、维护或局部恢复，但不会直接突破关键安全边界。
- **INFO**：建议、已接受风险、后续验证或不适用说明。

严重度必须结合实际爆炸半径和证据，不能只按关键词判断。

### 5. 输出报告

使用 [`templates/report.md`](templates/report.md)，默认写入：

```text
docs/reviews/YYYY-MM-DD-<topic>-ops-readiness.md
```

`<topic>` 使用通用、去标识化的短名称，不把客户、租户、集群、主机或内部项目真实标识写入文件名和 Git 历史。

总体结论规则：

- `PASS`：没有 BLOCKER/MAJOR，适用的关键控制均有足够证据，且不存在影响上线判断的 `NOT_VERIFIED`。
- `PASS_WITH_RISKS`：没有 BLOCKER；有限风险已经由有权接受风险的人明确接受，并记录依据、责任人/批准人、适用条件、期限或复审日期。尚未接受的 MAJOR、仅列为“上线前待办”的关键控制或影响上线判断的证据缺口不能使用此状态。
- `FAIL`：存在 BLOCKER、存在未修复且未由有权人员接受的 MAJOR、发布关键控制仍未完成，或关键安全/恢复领域无法验证到足以做上线判断。

报告按阻断问题、主要问题、次要问题、未验证项与证据缺口、已接受风险、不适用项、建议验证和证据分开呈现。

风险接受记录缺少批准人、依据、条件或期限时，维持 `FAIL`，不要替用户补齐或降级结论。

## 失败处理

| 触发条件 | 一线处理 | 仍无法解决 |
|---|---|---|
| 关键文件不存在、不可读或修订不明 | 列出缺失范围，只审查可确认材料 | 相关领域标 `NOT_VERIFIED`；影响上线判断时总体为 `FAIL` |
| 测试结果无命令、修订、时间或已明显陈旧 | 能确认测试确已执行但追溯信息不全时标为“有限 `TESTED`”；只能看到文字声明时降为 `DOCUMENTED`，并请求新鲜结果 | 不把它用于证明发布关键控制 |
| 文档、代码、测试和运行结果互相冲突 | 优先采用更直接、更新且可复现的证据，保留冲突说明 | 无法定界时标 `NOT_VERIFIED`，不选取最乐观结论 |
| 未找到某项控制的实现 | 扩大到真实调用链、配置和部署入口继续确认 | 只写“证据不足”，除非已有证据明确证明控制缺失 |
| 报告文件无法写入 | 在会话中按模板完整输出并记录目标路径和错误 | 明确尚未落盘，不宣称文件交付完成 |
| 建议验证需要生产变更、真实 SSH/Kubernetes 操作或破坏性测试 | 先给最小、可回退的验证方案和影响范围 | 未获明确授权时停止，保持 `NOT_VERIFIED` |

若需要执行生产变更、真实远程命令、破坏性测试或数据库迁移：

**🔴 CHECKPOINT · 🛑 STOP：先展示目标、命令/动作、爆炸半径、回退方式和证据用途，等待用户明确批准。**

## 红线与反例黑名单

- 不在报告中写入 Token、Cookie、私钥、密码、完整 kubeconfig、内部地址、PII、客户/租户/集群/主机真实标识、敏感日志正文或敏感请求体。Secret 只记录其存在位置与控制，不复制值；证据路径优先使用 repo-relative 路径，不泄露本机绝对路径。
- 不通过隐藏前端按钮来证明授权；必须检查后端强制执行。
- 不为通过审查而弱化鉴权、确认、审计、校验、超时或资源限制。
- 不把“没有收到证据”写成“代码里没有实现”，也不把文档承诺提升为静态或运行证据。
- 不把历史测试、保存的测试文本或 build 成功提升为 `RUNTIME_VERIFIED`。
- 不因清单中出现 Worker、Kubernetes 或指标就默认要求 MQ、Operator、HA、PDB、Tracing 或 OpenTelemetry。
- 不自动执行生产变更、破坏性测试、数据库迁移或真实远程命令。需要此类证据时，先提出最小验证方案并取得明确批准。
- 用户要求修复时，先将审查问题转成有边界的任务，再按适当的实现和验证流程处理。
