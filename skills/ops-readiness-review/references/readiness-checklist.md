# 运维就绪审查清单

先建立系统风险画像，再选择适用项。每个领域记录 `ASSESSED`、`NOT_APPLICABLE` 或 `NOT_VERIFIED` 及证据。

## A. 破坏性操作

适用于 Delete、Restart、Scale、Drain、Evict、Rollback、Execute、Kill 及批量变更。

- 后端是否按用户、角色和资源范围授权？
- 是否有与风险相称的确认或审批？
- 请求是否幂等，重复提交会发生什么？
- 是否限制目标范围、批量大小、并发和速率？
- 是否记录操作者、目标、动作、结果和请求 ID？
- 失败后能否回滚、重试或安全地人工恢复？

## B. 认证与授权

- Authentication 来源是否明确，失效和过期如何处理？
- 后端是否强制 RBAC/ABAC，而不是只隐藏按钮？
- 资源、Namespace、Cluster、Tenant 和环境边界是否受控？
- 列表、详情、写操作和异步任务是否使用一致的授权范围？
- 服务到服务调用是否使用最小权限身份？

## C. 审计

- 高风险动作是否记录操作者、时间、动作、目标、结果和请求 ID？
- 必要时是否记录安全的 Before/After 摘要？
- 异步任务能否关联发起请求、执行者和最终结果？
- 审计是否防止普通用户篡改，且有合理留存和查询方式？
- 是否避免记录 Secret、Token 和不必要的敏感正文？

## D. Secret 与凭证

- SSH key、kubeconfig/token、API token、DB 密码和 Cloud Credential 存在哪里？
- 静态与传输中是否受保护，是否进入前端、日志、错误或构建产物？
- 是否限制 Scope、有效期和可访问进程/用户？
- 是否支持轮换、吊销和失败后的安全处理？
- 测试、Mock 和示例是否使用去标识化占位数据？

## E. 远程执行

- 目标主机是否经过授权和校验？
- 命令是否预定义/白名单化，参数是否防止注入？
- 是否有连接、执行和空闲超时？
- 是否限制并发、输出大小和任务总量？
- Credential 是否隔离，输出是否脱敏？
- 是否支持取消、明确的失败状态和操作审计？
- 高风险命令是否需要审批或二次确认？

## F. Kubernetes 操作

- ServiceAccount/RBAC 是否为最小权限并按 Cluster/Namespace 隔离？
- Cluster Credential 是否隔离、轮换且不会发送到前端？
- 危险 Mutation 是否确认、审计并限制爆炸半径？
- List 是否分页，Watch 是否处理断线、过期 resourceVersion 和重连？
- API 调用是否有超时、速率限制和有边界的重试？
- 是否正确处理冲突、部分失败和目标状态变化？
- 普通 CRUD 是否避免无证据地引入 Operator？

## G. 异步任务

- 状态、发起人、目标、进度和错误是否持久化？
- Job 是否有幂等键或重复执行保护？
- Retry 是否有上限、退避和可判定的错误分类？
- 是否支持超时、取消和并发限制？
- Worker/进程重启后状态如何恢复或明确失败？
- 是否避免同一目标的冲突任务同时执行？
- 不需要独立 Worker/MQ 时，是否说明进程内任务的边界？

## H. API 可靠性

- 输入、资源范围、分页、排序和过滤是否校验？
- 错误响应是否稳定且不泄露内部细节？
- 外部调用是否有超时和有边界的重试？
- Mutation 是否考虑幂等、重复请求和并发冲突？
- 是否有请求 ID、速率/并发限制和合理的响应大小？

## I. 可观测性

- 是否有结构化日志及请求/任务关联标识？
- Health 与 Readiness 是否反映不同状态？
- 是否有与系统风险匹配的指标和错误可见性？
- 告警是否指向可行动的用户影响或资源风险？
- Trace 是否确有跨服务诊断需要；不要默认强制 OpenTelemetry。

## J. 数据生命周期

- 数据、任务结果、审计和日志的 Retention 与 Cleanup 是否明确？
- 备份、恢复及恢复验证是否匹配数据价值？
- Schema Migration 是否可回退或有兼容策略？
- 删除、匿名化和敏感数据处理是否符合要求？
- 是否限制日志、任务输出和历史数据无限增长？

## K. 部署

- 配置与 Secret 是否分离，环境差异是否明确？
- 是否有 Health/Readiness、Graceful Shutdown 和资源限制？
- 持久化数据、Migration、升级和回滚如何处理？
- 多实例时是否正确处理 Session、Scheduler、Job 和锁？
- Kubernetes 部署按需检查 requests/limits、readinessProbe、liveness/startupProbe、terminationGracePeriod 和 PDB；不适用时说明理由。

## L. 失败与恢复

至少回答适用的故障：

- 数据库不可用或恢复后会怎样？
- 目标 Kubernetes、SSH 主机或外部 API 不可达会怎样？
- 请求超时但远端动作可能已完成时如何判定？
- Worker/进程重启或任务重复执行会怎样？
- 部分目标成功、部分失败时如何呈现和恢复？
- 日志、指标或审计后端不可用时是否阻断关键操作？
- 操作者如何发现、诊断并安全恢复？
