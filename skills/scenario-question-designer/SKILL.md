# 个性化场景面试题设计

先把输入整理成可审核的场景题确认稿，再生成正式题目。场景必须考察信息获取、假设、证据、止损、恢复和权衡，不能只是给技术名词加一句“怎么排查”。

## 必读资料

开始前完整读取：

- `references/personalization-profile.md`：岗位、经历、难度和隐私边界。
- `references/scenario-brief-template.md`：确认稿格式。
- `references/scenario-quality-rubric.md`：场景、数据和推理质量标准。

只有用户确认 Scenario Brief、准备生成完整题目时，再读取 `references/question-template.md`。

## 边界

- 接受上游候选报告，但不要求其他 Skill 必须安装；也可独立处理用户直接输入。
- 区分用户事实、来源事实、教学性构造和待核实信息。
- 不把模拟场景写成真实事故，不把模拟值写成官方阈值或用户环境数据。
- 个人画像只调整场景相关性、复杂度和追问，不制造用户经历。
- 没有已有题目集合时不得声称“没有重复题”；只能做当前输入内的去重。
- Scenario Brief 未确认前不生成完整题目。
- 不操作题库、数据库、CLI 或外部系统，只输出通用 Markdown。
- 输出不得保留个人姓名、用户名、本地绝对路径、私有仓库、内部主机/IP、客户标识、账号或凭据。

## 固定输出路径

以调用时的工作目录为基准：

```text
./scenario-question-designer-output/
├── scenario-briefs.md
├── scenario-question-set.md
└── questions/
    └── <stable-id>.md
```

- 分析阶段只写 `scenario-briefs.md`。
- 用户确认后，每道题写入独立文件，并重建 `scenario-question-set.md` 索引。
- 目标文件存在时先说明覆盖范围；未经确认，不静默覆盖。

## 输出层级

- 默认输出精简 Scenario Brief：事实分类、六要素、关键数据、核心假设、处置判断和确认项。
- 质量检查全部通过时只写结论；只有发现矛盾、装饰性数据、隐私风险或待核实时才展开理由。
- 用户要求“详细确认稿”时，再展开完整推理链、难度调节和逐项质量审查。
- 参考答案、追问、易错点和防复发属于确认后的正式题目，不在默认 Brief 中提前展开。

## 异常与兜底

| 触发条件 | 一线处理 | 仍失败时的兜底 |
|---|---|---|
| 指定候选 ID 缺少正文、来源或确认状态 | 处理可验证的 ID，单独列出缺失项 | 不为缺失 ID 构造候选；要求补充上游条目 |
| 用户描述与实际读取材料主题不一致 | 列出预期主题和实际主题 | **停在确认点**，未经确认不得切换场景对象 |
| 事实互相矛盾 | 标记冲突及其影响，不选择性忽略 | 将候选置为待核实，不生成正式题目 |
| 信息不足以形成可回答场景 | 只补充能改变判断的教学性构造值 | 若核心环境、异常或处理目标仍不明确，先追问并停止生成 |
| 用户要求把构造值写成真实事故数据或官方阈值 | 明确说明构造值边界并改为教学性表述 | 无法保留事实边界时拒绝该写法，不伪造来源 |
| 已确认 ID 与当前 Brief 不一致或 Brief 已被修改 | 展示差异并要求重新确认 | 使用最后一次明确确认的版本，不合并猜测出来的变更 |
| 输出文件已存在 | 展示将新增、重建和保持不变的文件 | 未获覆盖确认时只展示草稿，不写文件 |

## 工作流程

### 1. 确认输入

接受：

- 候选审核报告中的 `SCENARIO_CANDIDATE`；
- Roadmap 或 Markdown 知识单元；
- 普通面试题；
- 用户提供的故障、事故或项目素材；
- 多个相关知识点组合出的合理生产情境。

记录纳入范围和排除项。若输入来自本地仓库，先读取适用的 `AGENTS.md`，来源只记录相对路径和标题路径。

如果提供已有题目目录，读取相关题目完整正文以检查实质重复；否则只检查本轮候选之间是否重复，并明确这一限制。

### 2. 建立个性化画像

按照 `personalization-profile.md` 使用用户已经提供的岗位、级别、JD、真实经历、强弱项和用途。只追问缺失后会改变核心场景或风险边界的信息。

没有画像时使用通用模式，不猜测年限、岗位或项目经历。

### 3. 分离事实、假设与待核实项

逐项标记：

- **用户提供事实**：用户明确陈述且允许用于题目。
- **来源事实**：可由指定材料支持。
- **模拟构造值**：为了形成可回答场景而设计。
- **待核实**：缺失会改变判断，不能自行确定。

输入包含真实事故时先去标识化。未经允许，不把真实公司、客户、规模、IP、时间或损失写入输出。

### 4. 构造场景六要素

明确：

1. 环境；
2. 异常现象；
3. 已知条件；
4. 排除条件；
5. 业务约束；
6. 要求候选人做出的处理判断。

继续设计影响面、紧急程度、多个可证伪假设、信息优先级、止损、恢复、验证、风险权衡和防复发方向。不要把所有常见原因排除到只剩命题人预设答案。

### 5. 设计高信号数据

按照 `scenario-quality-rubric.md` 检查延迟、吞吐、错误率、资源、连接、时间窗口、规模、版本和业务指标。

输入不足时，按需补充少量高信号模拟数据：

- 每个数据必须改变至少一项假设、优先级、风险或方案；
- 保留单位、基线、比较对象、统计口径和时间窗口；
- 数值之间保持合理量级和因果一致；
- 直接放入拟定题干，而不只留在分析表；
- 明确标记为模拟构造值，不能外推成通用生产阈值。

不要机械追求固定数量；没有判断价值的数据应删除。

### 6. 校准个性化难度

难度来自信息歧义、系统范围、组件跨度、时间压力、数据风险、业务约束和责任范围，而不是工作年限本身。

- 验证弱项：给出足够入口信息，观察知识结构和调查顺序。
- 验证强项或简历声明：增加机制、边界、取舍和恢复验证。
- 目标偏初级：减少冲突约束和跨组件因果。
- 目标偏高级：加入部分故障、不可逆风险、SLO/成本冲突或跨团队决策。

### 7. 输出 Scenario Brief

按 `scenario-brief-template.md` 写入 `scenario-briefs.md`。每个条目使用本轮稳定 ID，例如 `SCN-001`，并包含事实分类、场景六要素、模拟数据、推理链、质量审查、个性化依据、难度和用户确认项。

停在审核门。等待用户确认：

- 哪些 ID 生成；
- 哪些事实和构造条件保留；
- 最终难度和适合对象；
- 是否调整约束、数据或追问方向。

## 🔴 CHECKPOINT · Scenario Brief 确认

展示 Scenario Brief 后立即停止，不生成完整题目或更新场景题索引。

🛑 **STOP**：只有用户明确确认 ID、事实与构造条件、适合对象和难度后，才能进入步骤 8。对一个 ID 的确认不能扩展到其他候选。

### 8. 生成已确认的场景题

用户确认后：

1. 读取 `question-template.md`。
2. 只生成明确确认的 ID。
3. 保留确认的事实、构造条件、难度和考察目标。
4. 每题写入 `questions/<stable-id>.md`。
5. 生成 `scenario-question-set.md`，列出 ID、标题、领域、适合对象、难度、来源状态和文件链接。
6. 对输出做敏感信息、事实边界和数值一致性检查。

生成后报告实际文件、跳过项和仍需核实的事实。

## 上游候选契约

读取上游 `SCENARIO_CANDIDATE` 时优先使用以下字段；字段缺失时按“异常与兜底”处理，不猜测：

```yaml
candidate_id: QGA-004
source: relative/path.md > heading
knowledge_unit: 核心知识单元
assessment_goal: 核心考察目标
target_role: 目标岗位或通用
difficulty: 初级 | 中级 | 高级
personalization_boundary: 不得推断的个人经历
confirmed_constraints: 用户确认保留的条件
unresolved_facts: 仍待核实的信息
```

## 反例黑名单

- 不要把“某组件异常，怎么排查”包装成完整场景题。
- 不要用大量指标代替明确的处理判断。
- 不要排除所有常见原因，把题目变成唯一答案猜谜。
- 不要使用缺少单位、基线、窗口或判断作用的精确数值。
- 不要把连接、相关指标或时间重合直接写成唯一根因。
- 不要把模拟条件写成真实事故、官方阈值或用户亲历事件。
- 不要为了提高难度堆积无关数据或隐藏所有入口信息。
