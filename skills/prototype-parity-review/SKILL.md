# 原型一致性审查

判断 React + Mock 是否忠实实现已经批准的 HTML Prototype。HTML 是视觉与交互契约，React 是工程化实现；审查关注工程化过程中是否改变了已确认的产品设计，而不是把两者变成逐像素相同的截图。

默认只审查并记录证据，不修改 React、HTML 或产品规则。发现问题后由用户决定是否进入修复。

## 所处流程

```text
HTML Prototype
→ 人工原型评审
→ React + Mock
→ 原型一致性审查
→ 架构草案
```

`FAIL` 时停止，不进入架构草案。这个门禁不替代代码审查、真实后端 E2E 或最终人工验收。

## 输入

优先取得：

1. 已经获得人工批准的 HTML Prototype 路径或可访问 URL，以及批准记录或用户在当前会话中的明确确认。
2. React + Mock 项目路径、启动方式和可访问 URL。
3. 已批准的关键业务 Flow、目标路由和代表性 viewport。
4. 原型评审记录或用户明确批准的变更，用于区分“有意调整”和“实现偏差”。

如果缺少可比较的 HTML、React 实现、人工批准证据或关键 Flow 范围，停止并说明缺失项。可以继续做标为 `PRECHECK` 的非 Gate 预检，但正式 Gate 必须为 `FAIL`，且不得进入 Architecture Draft。无法取得完整 Flow 清单时，将未知范围标为影响 Gate 的 `NOT_VERIFIED`。

## 审查原则

- **以批准的 Prototype 为准**：组件库必须服务于原型，不能以 MUI、Ant Design 或其他默认样式覆盖原型语言。
- **比较可观察行为**：关注用户看到和操作到的结果，不要求 DOM、组件树或实现技术一致。
- **状态比静态首页更重要**：检查 Dialog、Drawer、Tab、筛选、分页、表单、Loading、Error、Empty、Success 和任务进度等状态。
- **真实渲染优先**：只读源码不足以证明视觉与交互一致。能运行时使用真实浏览器复现关键路径并保存必要证据。
- **不追求像素级自动 diff**：像素差可以辅助定位，但不是单独的通过标准。字体渲染、浏览器和操作系统差异需要人工判断。
- **不把新增功能自动算作改进**：未经批准的新入口、新流程或状态变化属于契约偏差。

## 工作流

### 1. 固定比较契约

记录 HTML 与 React 的版本或路径、启动命令、路由映射、viewport、认证/Mock 条件和已批准例外。不要在审查过程中悄悄更换基准。

把页面和关键状态整理为映射表：

```text
Prototype 页面/状态 → React 路由/状态 → 验证方式
```

### 2. 建立覆盖矩阵

逐页识别：

- 公共布局、Navigation 和信息架构；
- 页面核心信息与数据密度；
- 可触发的交互及其前置状态；
- 响应式断点或明确要求的 viewport；
- Loading、Error、Empty、Success 等非默认状态。

没有进入覆盖矩阵的区域，不得在最终报告中声称已验证。

### 3. 运行并采集证据

可运行时，分别打开 HTML 和 React，在相同 viewport、等价数据与等价状态下比较。按需使用浏览器截图、DOM 检查、控制台和网络证据，但只保留能支撑结论的材料。

如果受环境、依赖或认证限制无法真实运行：

- 继续完成能做的静态审查；
- 把对应项标为 `NOT_VERIFIED`；
- 不给出 Gate `PASS`。

### 4. 检查视觉一致性

读取 [`references/review-checklist.md`](references/review-checklist.md)，检查布局、层级、字体、间距、颜色、边框、阴影、密度、Navigation、Table/Card、Dialog/Drawer、图表和响应式行为。

重点寻找“组件库洗平”：虽然功能存在，但页面被统一改造成默认 Dashboard、默认圆角卡片、默认字体或默认间距，从而丢失原型的设计语言。

### 5. 检查交互一致性

沿批准的关键 Flow 实际操作，检查导航、点击、Tab、筛选、分页、表单、提交、取消、Dialog、Drawer、反馈状态、错误阻断和任务进度。

区分：

- `MATCH`：可观察结果与原型一致；
- `APPROVED_CHANGE`：不同，但有明确批准证据；
- `DEVIATION`：缺失、错误或未经批准的改变；
- `NOT_VERIFIED`：当前证据不足。

### 6. 判定严重度

- **BLOCKER**：关键 Flow 无法完成；核心 Navigation、信息架构或视觉语言被改变；缺失安全/确认步骤；未经批准新增会改变用户行为的能力。
- **MAJOR**：重要页面、状态或交互明显不一致，但仍有绕行路径。
- **MINOR**：不改变主要理解和流程的局部差异，例如小范围间距、文案或非关键响应式问题。
- **INFO**：已批准变更、环境限制或建议观察项。

### 7. 输出门禁报告

使用 [`templates/report.md`](templates/report.md)，默认写入：

```text
docs/reviews/YYYY-MM-DD-<topic>-prototype-parity.md
```

门禁规则：

- `PASS`：关键页面和 Flow 均已真实验证，无 BLOCKER/MAJOR/MINOR，且没有影响门禁的 `NOT_VERIFIED`。
- `PASS_WITH_NOTES`：无 BLOCKER/MAJOR，仅有不影响批准意图的 MINOR、已批准变化或非关键限制。
- `FAIL`：存在 BLOCKER/MAJOR，或关键范围无法验证。

报告必须将结论绑定到页面、状态、Flow 和证据，不能只写“整体一致”。

`FAIL` 只授权输出审查结论，不自动授权修改产品。用户未在当前请求中明确要求修复时：

**🔴 CHECKPOINT · 🛑 STOP：交付 FAIL 报告后停止，等待用户确认修复范围。**

## 失败处理

| 触发条件 | 一线处理 | 仍无法解决 |
|---|---|---|
| HTML、React、批准记录或关键 Flow 不完整 | 列出缺失项，只做标为 `PRECHECK` 的静态检查 | Gate 为 `FAIL`，关键范围标 `NOT_VERIFIED` |
| build 或启动命令失败 | 保存命令、首个有效错误和环境信息，区分依赖、配置与实现问题 | 完成可做的静态检查，不给 `PASS` |
| build 成功但页面白屏、根组件崩溃或控制台有阻断错误 | 以真实运行结果为准，记录 runtime 证据并判定受影响 Flow | 将核心页面不可用判为 BLOCKER；不要用 build 记录覆盖运行失败 |
| 认证、权限或前置数据无法建立等价状态 | 使用批准的 Mock/测试身份和去标识化数据重试 | 对受影响页面和 Flow 标 `NOT_VERIFIED`，不推断一致 |
| HTML 与 React 的数据、viewport 或版本不等价 | 恢复同一比较条件并重新采证 | 无法对齐时停止该项比较并说明 Gate 影响 |
| 历史验证记录与当前运行结果冲突 | 优先采用可复现的当前证据，并记录修订、时间和复现方式 | 将冲突证据列入报告，不给 `PASS` |
| 报告文件无法写入 | 在会话中按模板完整输出，并保留目标路径和写入错误 | 明确报告尚未落盘，不宣称交付文件完成 |

## 红线与反例黑名单

- 不在报告或截图说明中暴露密码、Token、Cookie、真实客户信息或内部地址。
- 不为通过审查而自动删除权限、确认、审计或错误处理。
- 不把 Mock 成功路径当作真实后端、权限或生产可靠性的证明。
- 不把 build 成功、源码相似或历史 PASS 记录提升为当前运行验证。
- 不因证据缺失就断言某项实现不存在；使用 `NOT_VERIFIED` 并说明缺口。
- 不把所有视觉差异都升级成 BLOCKER；按批准意图和关键 Flow 的影响判级。
- 用户要求修复时，先确认允许修改的范围，再做最小变更并重新运行受影响检查。
